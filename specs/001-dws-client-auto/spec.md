# Feature Specification: DWS 官方客户端 AUTO 写入升级

**Feature Branch**: `FLINK-39327`

**Created**: 2026-10-10

**Status**: Draft — 规格、技术规划与任务拆分已完成，待实施；运行验收未执行

**Input**: 用户在版本及大小写敏感缺陷调研后确认：“采用官方客户端 AUTO 路线”。本规格承接该决策：升级 DWS 写入能力，默认自动选择写入方式，保留主键表 CDC 能力，以至少一次投递及主键幂等保证恢复后的最终结果，并明确兼容和迁移边界。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 默认自动写入并保持最终数据正确 (Priority: P1)

作为数据同步任务维护者，我希望无需手工选择小批量和大批量写入方式，就能同步主键表的新增、修改及删除，并在任务追平后获得与源端一致的目标数据。

**Why this priority**: 这是用户选择官方 AUTO 路线的核心收益，也是替换当前写入路径的前提。

**Independent Test**: 对固定主键表分别输入稀疏和持续批量事件，包括同键连续更新、删除后重建、复合主键和主键变化；任务追平后逐键逐字段与参考结果比对。

**Acceptance Scenarios**:

1. **Given** 未配置写入模式的有效主键表任务，**When** 分别输入小批量和大批量事件，**Then** 任务采用 AUTO 策略，目标结果一致，并可从运行证据确认实际选择的写入路径。
2. **Given** 同一主键发生新增、连续更新、删除和再次新增，**When** 所有事件完成同步，**Then** 目标表只保留该主键最后应有的状态，已删除且未重建的记录不存在。
3. **Given** 源记录主键从旧值变为新值，**When** 同步完成，**Then** 旧键记录不存在、新键记录内容正确；这不受仅针对独立删除事件的关闭选项影响。
4. **Given** 未声明主键的表，**When** 表首次进入任务，**Then** 系统在写入该表业务数据前拒绝并说明主键要求。

---

### User Story 2 - 故障重放后恢复最终一致 (Priority: P1)

作为运维人员，我接受故障后部分事件被再次投递，但希望恢复并追平后不丢数据、不残留过期记录；写入失败必须使任务进入可观察的失败和恢复流程。

**Why this priority**: AUTO 原生写入不提供原有提交路径所追求的 checkpoint 级事务可见性，必须准确说明和验证替代保证。

**Independent Test**: 在缓冲未写出、部分写入完成、数据库已接收但客户端未获确认、恢复点确认前后分别注入故障；恢复后对比最终数据。

**Acceptance Scenarios**:

1. **Given** 数据已写入而对应恢复点尚未成功，**When** 故障恢复导致事件重放，**Then** 追平后每个主键的内容与参考结果相同，允许恢复过程中出现中间状态。
2. **Given** 尚有缓存或异步写入未完成，**When** 系统准备确认恢复点或正常结束输入，**Then** 必须等待对应数据写入完成；失败时不得把该批数据当作已成功写入。
3. **Given** 网络中断或持续不可恢复的写入错误，**When** 达到配置的重试或超时边界，**Then** 任务报告失败及上下文，不静默丢弃记录，也不无限等待。
4. **Given** 多个并发写入任务处理同表数据，**When** 同键事件连续到达并经历重试，**Then** 追平后旧值不得永久覆盖新值；主键修改涉及的旧键删除也必须满足该要求。

---

### User Story 3 - 大小写字段与表结构变更正常同步 (Priority: P1)

作为任务维护者，我希望大小写敏感表无需规避写入模式，且表结构变更不会使后续记录使用过期的字段定义。

**Why this priority**: 这是已知 COPY_MERGE 缺陷和 CDC schema 演进的直接验收边界。

**Independent Test**: 使用含大小写混合 schema、表名、普通字段及复合主键的表，分别运行 AUTO 和显式 COPY_MERGE，并穿插当前支持的表结构变更。

**Acceptance Scenarios**:

1. **Given** `case-sensitive=true` 且字段包含混合大小写，**When** 使用 AUTO 或显式 `copy_merge` 同步新增及更新，**Then** 引用正确字段，不出现因字段大小写折叠导致的 SQL 失败，也不因该开关强制更改用户指定的模式。
2. **Given** `case-sensitive=false`，**When** 同步既有大小写不敏感任务，**Then** 保持原有标识符归一化约定。
3. **Given** 旧表结构下仍有未完成写入，**When** 到达支持的表结构变更，**Then** 先完成旧数据写入，再应用变更并刷新字段认知，之后才处理新结构的数据。
4. **Given** 表结构变更前的刷新或变更本身失败，**When** 任务处理后续数据，**Then** 必须停止推进并报告失败，不能带着过期结构继续写入。

---

### User Story 4 - 调优参数有效且内存受控 (Priority: P2)

作为运维人员，我希望批量、时间和内存配置确实控制写入行为，并能看出延迟来自缓冲、数据库写入还是重试。

**Why this priority**: 当前路径接受部分不生效的原生参数；升级需要让调优行为可解释、可验证。

**Independent Test**: 分别改变批量阈值、刷新间隔和缓存预算，对比实际写入时机及缓冲趋势；再输入非法配置与旧参数别名检查提示。

**Acceptance Scenarios**:

1. **Given** 启用自动刷新，**When** 批量阈值或刷新时间条件先满足，**Then** 待写数据进入刷新流程，无需等到下次恢复点；数据库阻塞时体现背压或超时而非承诺固定完成延迟。
2. **Given** 持续输入超过下游处理能力，**When** 缓冲达到配置预算，**Then** 系统施加背压或受控失败，不无限积累待写数据；关闭定时自动刷新也不能关闭内存保护。
3. **Given** 使用受支持的旧参数，**When** 启动任务，**Then** 参数单位和映射明确；无法继续支持、冲突或非法的参数给出明确诊断，不能静默接受后忽略。
4. **Given** 自动写入及重试正在发生，**When** 查看任务诊断信息，**Then** 能识别生效模式、缓冲规模、写入耗时及失败/重试情况，诊断信息不包含密码或完整业务记录。

---

### User Story 5 - 可控迁移现有任务 (Priority: P1)

作为运维人员，我希望在了解语义变化、旧状态兼容范围及回退条件后迁移任务，而不会因直接加载旧状态而丢失尚未提交的数据。

**Why this priority**: 更换提交路径涉及已有任务状态和遗留中间数据，是发布的必要条件。

**Independent Test**: 在具有待提交数据的旧任务上按迁移指南演练停止、处理在途数据、建立恢复边界、启动新任务及回退，并核对源目标数据与遗留资源。

**Acceptance Scenarios**:

1. **Given** 旧任务有在途写入与恢复状态，**When** 执行迁移，**Then** 按已验证步骤处置在途数据并保留可追溯的恢复边界；不得通过默默丢弃旧状态完成启动。
2. **Given** 用户尝试加载尚未验证兼容的旧状态，**When** 进行部署前兼容检查或启动，**Then** 明确阻止该迁移方式并提供支持的路径。
3. **Given** 新版本需要回退，**When** 按回退指南操作，**Then** 可恢复旧版本运行并通过重放或重新同步使最终数据正确；不承诺新旧状态可以双向直接加载。
4. **Given** 存在旧中间表或提交记录，**When** 执行遗留清理，**Then** 只有明确归属本任务且确认无在途用途的资源可进入清理范围，业务表及其他任务资源不受影响。

### Edge Cases

- 无主键、空主键、复合主键、主键变化与同键高频交错更新。
- 大小写混合表名/字段、保留字标识符；带内嵌引号等特殊标识符如不支持，必须明确拒绝而非静默改名。
- 空值、Unicode、时间类型和高精度数值；非法字符不得在没有既定或显式配置规则的情况下被新增的兼容逻辑静默替换。
- AUTO 切换阈值附近的批量大小、稀疏流、空刷新、多表同时达到内存预算。
- 写入完成但响应丢失、恢复点取消、连续恢复、正常结束输入、刷新期间关闭。
- schema barrier 与数据重放交错、表更名/删除/截断和元数据缓存过期。
- 旧配置时间单位变化、同一参数新旧名称同时出现、重试后异步异常。
- 迁移时残留待提交数据、旧恢复状态不兼容、多个任务共享目标库。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 新写入路线 MUST 默认使用 AUTO，显式受支持模式优先；系统 MUST 能提供实际生效模式的运行证据。（US1、US4）
- **FR-002**: 系统 MUST 维持主键表新增、替换、更新、删除及复合主键支持；无有效主键的表 MUST 在业务数据写入前被拒绝。（US1）
- **FR-003**: 系统 MUST 将主键变更处理为旧键消失、新键存在的结果，并保持既有独立删除事件开关的语义。（US1）
- **FR-004**: 系统 MUST 在文档与迁移说明中明确至少一次投递、允许重放及最终一致的保证；不得声称 checkpoint 级事务可见性或全局原子提交。（US2、US5）
- **FR-005**: 在源事件可重放、同键顺序可保持、目标表无未协调外部写入的前提下，系统 MUST 在恢复追平后与源端最终主键状态一致，包括最终删除。（US2）
- **FR-006**: 系统 MUST 在确认相关恢复边界及正常结束输入前等待对应待写数据完成；异步失败 MUST 传播为任务失败。（US2）
- **FR-007**: 重试及等待 MUST 遵守明确的配置边界；不可恢复错误 MUST 可诊断且不得被静默吞掉。（US2、US4）
- **FR-008**: 系统 MUST 保证同键事件在并发、重试和恢复后不会造成永久的旧值覆盖新值；同键顺序约束也适用于主键变化的删除操作。（US2）
- **FR-009**: 大小写敏感开关 MUST 在受支持标识符范围内对 AUTO 和 COPY_MERGE 均生效，且不得仅因开启该开关改变写入模式。（US3）
- **FR-010**: 系统 MUST 保持大小写不敏感任务既有归一化行为；无法支持的标识符 MUST 明确诊断。（US3）
- **FR-011**: 受支持的 schema 变更 MUST 与旧数据完成写入、新元数据生效及新数据写入建立明确先后关系；任一阶段失败 MUST 停止推进。（US3）
- **FR-012**: 系统 MUST 提供有效的批量条数、刷新时间及缓冲预算控制；在下游受阻时通过背压或受控失败保持缓冲有界。（US4）
- **FR-013**: 系统 MUST 发布新旧配置兼容映射及单位说明，明确冲突处理规则；无法支持的配置不得静默失效。（US4）
- **FR-014**: 系统 MUST 提供生效配置、写入/刷新耗时、缓冲规模及错误/重试诊断，并保护凭据和业务数据。（US4）
- **FR-015**: 发布前 MUST 提供经演练的迁移及回退路径，明确旧状态兼容性、在途数据处理、恢复边界和遗留资源归属。（US5）
- **FR-016**: 新路线 MUST 不再要求原有自研中间表提交协议；遗留资源清理 MUST 独立于正常启动，且不得误删业务或其他任务资源。（US5）
- **FR-017**: 系统 MUST 保留当前已支持的数据类型及事件转换语义；新增非法字符处理策略必须显式说明，不能以静默丢失数据换取写入成功。（US1、US3）
- **FR-018**: 发布前 MUST 在现有两代受支持运行环境中验证配置、大小写、写入、恢复和迁移契约；兼容性差异必须明确列出。（US1～US5）

### Key Entities *(include if feature involves data)*

- **同步任务**：包含源端恢复边界、目标表集合、写入配置和运行状态的一次持续同步。
- **主键表与标识符**：表结构、主键、字段名称及其大小写规则，决定数据定位与更新结果。
- **变更事件**：记录前后值、操作类型和相对顺序；主键变化会影响两个键的最终状态。
- **写入批次与缓冲预算**：待写事件集合、大小、等待时间及完成/失败状态。
- **恢复边界**：已确认可安全重放的位置；不代表目标表跨任务或跨表的原子事务。
- **迁移记录**：旧状态来源、在途数据处置、恢复位置、核对结果、遗留资源清单及回退条件。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新增、连续更新、删除后重建、复合主键、主键修改五类事件序列，在正常运行及故障恢复追平后均为零缺失、零多余主键、零字段差异。（FR-002～008、017）
- **SC-002**: 大小写敏感/不敏感与自动/显式合并模式的四组组合全部通过混合大小写字段验收；零因标识符大小写错误产生的失败。（FR-009、010）
- **SC-003**: 对缓冲中、写入中、数据库已接收但响应丢失、恢复边界确认前、确认后五个故障窗口分别执行至少一次恢复演练；全部达到 SC-001，失败批次被错误报告为成功的次数为零。（FR-004～008）
- **SC-004**: 对每个公开保留的写入参数至少提供一项生效或拒绝证据；所有兼容别名、非法值及冲突组合均有确定结果，静默忽略项为零。（FR-012～014）
- **SC-005**: 在固定资源预算下执行至少 30 分钟的下游限速场景；无内存耗尽，缓冲在预先冻结的测量容差内受控，并观测到背压或配置规定的受控失败。（FR-012）
- **SC-006**: 使用相同资源、数据集、最终正确性标准分别对稀疏和持续批量负载进行新旧路线各至少三次测量，交付吞吐、端到端延迟、峰值内存及恢复边界耗时的完整对比；语义差异和性能回退必须明确说明，不得仅凭单次峰值宣称提升。（FR-001、012、014）
- **SC-007**: 迁移和回退各完成至少一次含在途数据的演练，最终数据差异为零，误删业务或其他任务资源为零；操作人员可以依据指南完成流程且不存在未解释的状态丢弃步骤。（FR-015、016）
- **SC-008**: 当前支持的每类结构变更均覆盖成功与失败场景，失败后继续按过期结构写入的次数为零；两代受支持运行环境的必验项全部有通过或阻断发布的明确结果。（FR-011、017、018）

## Assumptions

- 本次功能描述来自上文已确认决策，不要求用户重新填写空命令参数。需求目标是 DWS Pipeline Connector，不是 helper 项目其他正在进行的功能。
- 已确定采用官方客户端 AUTO 路线，拟升级目标为 dws-client 2.1.0.6。该版本及保留 SinkV2 接口属于会话已确定的技术约束；具体依赖组合、类结构、参数默认值和生命周期实现留在技术规划中展开。
- 2026-10-10 规划阶段补充决策：用户要求保留单表多 writer，授权扩展公共分区层处理主键变更；不采用按表固定单 writer 的简化方案。公共变更需由 DWS 显式启用，其他 connector 保持原行为。
- 原生投递允许重放；业务接受目标数据在恢复过程中的中间可见状态。最终一致以源端有序可重放、已声明主键唯一、同键路由正确、无未协调的目标端外部写入为前提。
- 保留当前主键表约束和现有支持的数据/结构事件范围；不新增无主键表保证，不扩大数据库内核或运行环境的支持范围。
- 本次不包含 Direct-DN 默认启用、compareField 新能力、双写入引擎、全局事务或自动删除遗留资源。
- 旧状态直接恢复尚未验证；必须在技术规划和演练中确定支持的迁移路径，不预设兼容，也不默认允许丢弃状态。
- 性能无已确认的提升百分比目标；SC-006 是证据交付要求，不将未实测的吞吐收益写成承诺。性能回退在发布前必须显式评估。
- SC-005 的运行时长为初始验收约定；资源预算、缓冲测量容差和工作负载在技术规划中冻结并记录，不能测试后调整标准以宣称通过。
- 真实数据库与故障演练环境是运行验收依赖；当前规格检查通过不代表升级、恢复或迁移已经实测通过。
- 参考依据：[华为写入与恢复说明](https://support.huaweicloud.com/tg-dws/dws_07_0184.html)、[版本变更说明](https://support.huaweicloud.com/tg-dws/dws_07_0178.html)、[客户端配置](https://support.huaweicloud.com/tg-dws/dws_07_0175.html)。已核查的问题修复及当前代码路径来自本会话调研，发布时仍须用拟交付制品复验。
